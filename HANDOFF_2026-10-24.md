## 1. Where we are

The cache is now fast enough that it is no longer the bottleneck: ~70–100×
faster than a full forward of every mutant, with ~10× less training memory.
Accuracy-wise the approximation looks nearly free on sparse data and costly on
dense data, but **no comparison to published numbers is valid yet** — see §4,
which is the whole point of the next change.

## 3. Results so far (none of them comparable to the literature yet)

**Speed** (esmc_300m bf16, A6000). Ragged vs a full forward of every mutant:
BRCA1 eval 278 → 20,183 var/s (~73×), train 77 → 8,110 var/s (~105×), peak
memory 23 → 2 GiB. GB1 (dense) ~29× eval, ~42× train. Fused flex
cross-attention alone was 2.5× eval / 2.0× train over the old fp32 matmul path
with 2.4–2.8× less memory. Training memory is ~1.4 MiB per mutated position,
so ~28k substitutions per step fit in 40 GiB (per-layer checkpointing would
buy 10–20× more and is not implemented).

**Approximation cost** (PLAN 22, 3 seeds, `experiments/cache_vs_exact_accuracy.csv`).
Train-through (each backend trained *and* scored on its own terms): Tsuboyama
+0.030 ± 0.069 for exact, BRCA1 −0.008 ± 0.009, FLIP GB1 +0.004 ± 0.128 — no
significant gap, but GB1 has only 381 train rows so it could not have shown one.
Same-weights (cache-trained, scored through exact): −0.03 to −0.07.

**METL GB1 Rosetta, test = 50k of METL's supertest** (median of 3 seeds,
`experiments/metl_gb1_scaling.csv`):

| train | 900 | 3,600 | 14,400 | 57,600 | 115,200 |
|---|---|---|---|---|---|
| ρ@all | 0.839 | 0.912 | 0.934 | **0.955** | 0.952 |

Two things to carry forward: it **plateaus at ~58k** (so more data alone will
not help; capacity/budget/approximation is binding), and the exact-backend
control on these same weights drops hard and erratically (−0.08, −0.22, −0.37,
−0.08, −0.22 across sizes, seed 0) — expected, since METL GB1 is the densest
case we have (L=56, depth 3–5), but it means the cache-trained head leans
heavily on cache-specific features here.

Hyperparameters (chosen on **val** only, never test): `--loss rank --lr 3e-3`.
Pairwise rank ≫ MSE for Spearman (0.949 vs 0.820 at ds16000; mse_rank collapses
to 0.024 at lr 1e-2). Val curve plateaus ~epoch 9 and gives back only 0.004 by
epoch 14, so the grid uses a fixed epoch budget with `--no-select-best`.

## 4. Goal for the next change

**Get to a comparison that is actually apples-to-apples. Until then the numbers
above mean nothing against METL.** Three mismatches, in priority order.

### 4.1 Task mismatch (the blocker)

We train single-task on `total_score`. METL-Local pretrains **multi-task over
~55 standardized Rosetta attributes** (MSE), then reports Spearman on total
score. Ours is the easier problem, so 0.955 vs their 0.91 is not a win.

To match:
- `mutant_cache/data/metl.py` currently keeps only `total_score`; the canonical
  schema (`data/schema.py`) has a single `score` column, so the other 54
  attributes need a side table (e.g. `attributes.parquet` keyed by
  `score_set_id, mutant`) rather than a schema change.
- `VariantEffectModel` is scalar throughout (`additive_proj: Linear(d, 1)`,
  `inter_mlp` → 1, `assay_bias/scale`, `VariantPrediction.pred` as `(N,)`).
  Multi-task needs an `n_targets` config and touches the losses and eval too.
- METL ships `standardization_params/` (`energy_means_all.tsv`,
  `energy_stds_all.tsv`) next to the Rosetta data, so their normalisation is
  reproducible exactly.
- Expect our headline to *drop*: the probe showed MSE far worse than the rank
  loss for Spearman. That is the honest comparison.

**Cheaper alternative worth considering first:** METL's *DMS* benchmark is a
scalar task, so it needs **no model changes** — `metl_gb1_dms` is already built
(536,084 variants) and METL's own resampled grid is present at
`metl-pub/data/dms_data/gb1/splits/main/resampled/` with sizes
10, 20, 40, 80, 160, 320, 640, 1280, 2560, 5120, 10240, 20480. Those splits
still need converting into our split-table format (as `metl.py::build_rosetta`
already does for the Rosetta grid). This is their headline figure and a direct
head-to-head for our architecture. Caveat: METL-Local is Rosetta-pretrained
before DMS fine-tuning, so matching their *pipeline* means pretraining first.

### 4.2 Comparator numbers are approximate

Per the `metl-benchmark-targets` memory note, the METL-Local targets were read
off paper Figures 2/3 with no numeric source data published. `metl-pub` ships
**only** `dms_data` + splits + `datasets.yml` — no metrics or prediction files
(checked). So before claiming a head-to-head, find exact numbers: check the
`gitter-lab/metl` code repo, the paper's supplementary/source data, or run
their released checkpoints on these splits. **This was the open thread when
this session ended.**

### 4.3 Scale mismatch

58k–115k train rows vs METL's ~9.5M (`rosetta/gb1/splits/standard_tr0.8_tu0.1_te0.1_*/train.txt`).
One epoch over 9.5M is ~1 h at our measured ~2,400 var/s, so it is affordable —
but given the plateau in §3, raise capacity (LoRA rank, `--shared-lora-r`)
before buying more data.

### 4.4 Train/val loss monitoring (requested, not implemented)

`harness.py` logs `train_loss` per epoch and Spearman on **one** split
(`--eval-split`), so overfitting is only visible through the metric, and only on
whichever split is being reported. Needed: train **and** val loss at every eval
point in `metrics.jsonl`, without selecting on test. Suggested shape — a
`--monitor-val` flag that builds the val partition's batches alongside the
reported split and logs its loss and Spearman; `train()` already has the loss
function and the eval hook, so this is a contained change in
`harness.py::train` / `evaluate`.

## 5. Traps already hit (do not re-learn these)

1. **`--control-backend recompute` never measured the approximation.**
   `recompute` is the cache's *own* bruteforce oracle — same clamped maths — so
   its accuracy delta is ~0 by construction. `exact` is the real PLAN 22
   control. `HANDOFF.md` §6.6 still says to use `recompute` on GB1; that advice
   is wrong and should say `exact`.
2. **METL uses two index conventions internally**: Rosetta files are
   **1-indexed**, DMS files are **0-indexed**. `metl.py::_offset` re-derives it
   per build and refuses unless one offset reproduces the wild type at every
   position; the repo's WT report then found 0 mismatches over 602,094 and
   1,071,123 substitutions. Also METL's GB1 wild type (`MQYKLILNG…`, 56 aa) is
   **not** FLIP GB1's (`MTYKLILNG…`, 265 aa).
3. **flex_attention silently falls back** when dynamo exceeds its recompile
   limit, which looked like a 10× slowdown. Fixed by padding ragged rows to a
   multiple of 128, giving each call site its own compiled wrapper, and
   compiling the block-mask builder. A sweep over 8 lengths × 6 batch sizes now
   adds no new graphs. If ragged ever gets mysteriously slow, check
   `TORCH_LOGS=recompiles` first.
4. **Chunking must not hand batch-shaped hooks a slice.** The model's
   extra-embed hook closes over all N variants, so the first `forward_variants_exact`
   crashed/misaligned when it recursed over N. Regression test:
   `test_exact_chunking_with_batch_hooks`.
5. **Replicate rows leak across splits.** Tsuboyama/BRCA1 have repeated
   `(score_set_id, mutant)` rows (BRCA1: 15,966 rows for 9,419 unique mutants),
   so splits must be assigned per *unique* mutant.
6. A driver that reports `rc=$?` after a pipeline reports the pipe's status, not
   the run's — the first cache-vs-exact grid hid 6 crashes behind `rc=0`.
   Likewise grepping the *last* `ρ@all=` picks up the control line, not the
   model's.
